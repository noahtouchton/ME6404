# ME6404

## Final project: optimal crane maneuvers around obstacles

Two ways of planning a vibration-free move for the tower crane under the
fixed hardware limits:

| Folder | Method | What it solves |
|---|---|---|
| [`Demo Code/`](Demo%20Code) | **Indirect**: Pontryagin's minimum principle, a two-point BVP solved with `bvp4c` | Swing the payload around a pin the trolley can't reach around, then settle back at the start. Exports the crane GUI's Excel upload. |
| [`Direct Collocation/`](Direct%20Collocation) | **Direct**: trapezoidal collocation, a nonlinear program solved with `fmincon` (SQP) | Move between any two rest poses with free final time, keeping the payload clear of box and cylinder obstacles. |

Both use the same hardware limits:

| | trolley x | hoist l | slew θ |
|---|---|---|---|
| range | 0 – 0.925 m | 0 – 1.450 m | free |
| max velocity | 72.6 mm/s | 30 mm/s | 32.4 °/s |
| max acceleration | 72.6 mm/s² | 30 mm/s² | 32.4 °/s² |

```

├── Demo Code/            ← PMP / bvp4c pin swing-around + lab hot-tune script
└── Direct Collocation/   ← fmincon trapezoidal collocation with 3D obstacles
```

## Direct Collocation

The crane is modeled as a 3D spherical pendulum on a slewing trolley. The
inputs are the three drive accelerations:

- state `x = [x; l; θ; φ; ψ; ẋ; l̇; θ̇; φ̇; ψ̇]` (10 states; φ and ψ are the two swing angles)
- input `u = [ẍ; l̈; θ̈]`
- the dynamics are control-affine: `ẋ = A(x) + B(x)·u`

### Files

| File | What it does |
|---|---|
| `eom.m` | Derives the EOMs symbolically (kinematics plus the transport theorem, projected onto the swing directions). Splits them into `A(x)` and `B(x)` (`B = ∂f/∂u`, `A = f(x, 0)`) and writes `crane_AB.m`. Run it again only if the model changes. |
| `crane_AB.m` | Generated by `eom.m`. Don't edit. |
| `dynamics.m` | `x_dot = dynamics(x, u)`, which evaluates `A(x) + B(x)*u` (g = 9.81). |
| `obstacle_sdf.m` | Signed distance from the payload sphere (radius `R_pay`) to a `'box'` or `'cylinder'` obstacle. Positive means clear. Shared by the optimizer and the sim. |
| `optimize.m` | The optimizer. Set N, the limits, the start and end poses, and the obstacles at the top, then run it. Writes `trajectory.mat`. |
| `sim_trajectory.m` | Loads `trajectory.mat` and runs the trajectory through `ode45`. See the next section. |

### `sim_trajectory.m`

- Drives `dynamics.m` with the optimal inputs: u is linear between nodes, which matches the trapezoidal rule.
- Then coasts for 5 s with u = 0 to show any residual swing.
- Reports:
  - the collocation error
  - the end-pose error
  - the residual swing
  - the limit checks
  - the minimum clearance to each obstacle
- Plots the states and inputs, marking t_f, plus a top view with the obstacles.
- Plays a 3D animation with the obstacles drawn.

### The NLP in `optimize.m`

- **Decision vector:** `Z = [x at the N+1 nodes, u at the N+1 nodes, t_f]`.
- **Cost:**
  - Effort: `½ uᵀR u` with Bryson's rule, `R = diag(1/u_max²)`, integrated with the trapezoidal rule.
  - Time: plus `w_t·t_f`, so t_f is free and traded off against effort.
- **Dynamics (equality constraints):** `x_{k+1} − x_k − ½Δt (f_k + f_{k+1}) = 0`, with `Δt = t_f/N`.
- **Obstacles (inequality constraints):**
  - At every node, `−sdf(p_payload, obstacle) ≤ 0`.
  - The payload position is in the ground frame, with Z measured up from the floor and the jib at height `H_jib`.
- **Bounds:**
  - The state and input limits above.
  - The start and end states pinned, at rest with zero swing.
  - `t_f ∈ [tf_min, tf_max]`.

### Obstacle format (in `optimize.m`)

```matlab
obs(1).type = 'box';       obs(1).center = [X; Y; Z];  obs(1).half = [hx; hy; hz];
obs(2).type = 'cylinder';  obs(2).xy = [X; Y];  obs(2).R = r;  obs(2).z = [z_bottom; z_top];
```

`optimize.m` saves `obs`, `H_jib` and `R_pay` into `trajectory.mat`, so the sim
always draws and checks the same obstacles the optimizer used.

### Workflow

1. Run `eom.m`, only after a model change. It regenerates `crane_AB.m`.
2. Edit the poses and obstacles in `optimize.m` and run it. It writes `trajectory.mat`.
3. Run `sim_trajectory.m` to check and animate the result.

`trajectory.mat` is git-ignored like every other `.mat` file, so run
`optimize.m` once after cloning.

## Demo Code

The payload has to get around a pin that the trolley can't reach around. It
**swings** behind the pin, then settles back at its start with no residual
vibration. The trajectory comes straight from **Pontryagin's minimum
principle**: a two-point boundary value problem solved with `bvp4c`. It's
exported as the crane GUI's continuous-velocity Excel upload
(`time_s, trolley_pct, slew_pct, hoist_pct` at 0.05 s).

### Layout

```
Demo Code/
├── lab_tune.m          ← the lab script: maneuver + lab corrections -> solve -> check -> .xlsx
├── run_sim.m           ← replay/animate the last solution (no solving)
├── theory/             ← the math, readable
│   ├── EOM.m             dynamics -> cost -> H -> u* (∂H/∂u = 0) -> costates (λ' = -∂H/∂x)
│   └── pmp_bvp.m         boundary conditions + transversality (H(t_f) = 0) handed to bvp4c
├── engine/             ← behind the scenes: things you shouldn't need to touch
│   ├── hidden_settings.m hardware limits, cost weights, wall stiffness, solver tolerances
│   ├── solve_maneuver.m  warm/cold start, continuation, wall hardening, minimum time
│   └── ...               problem setup, initial guess, geometry, checks, preview plot
├── export/             ← the .xlsx upload + an open-loop replay of exactly that file
├── generated/          ← written by theory/EOM.m (don't edit)
├── archive/            the original single-file simulator
├── results/            solution.mat: the last solve, used as the warm start (git-ignored)
└── uploads/            the .xlsx files (+ the .mat that made each one) (git-ignored)
```

### In the lab

1. Open `Demo Code/` in MATLAB and run `lab_tune` (cold start ~10 s, warm re-solve ~2 s).
2. Upload the printed `uploads/trajectory_*.xlsx`.
3. Watch the run. Change the knob in section 2 of `lab_tune.m` that matches what
   you saw (the symptom → knob table is in the file), then run it again. If only
   `axis_gain` changed, it re-exports without re-solving.

After changing the model or the cost in `theory/EOM.m`, run it once to regenerate
`generated/`. The parameter order is shared automatically through
`generated/param_names.m`.
